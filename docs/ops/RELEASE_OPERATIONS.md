# Athena 发布与运营控制

> 责任项：ATH-OPS-001。生效范围：Desktop Direct、Steam、Athena Cloud、iOS、Android。当前阶段：Prelaunch。本文定义流程，不代表人员、账号、证书、状态页或平台审批已经就绪。

## 1. 不可越过的发布门

任一目标平台出现以下任一条件时，该平台必须是 **No-Go**：

1. 存在 `Severity = P0` 且 `Status != Closed` 的适用问题；
2. 缺少平台账号、AppID/Bundle ID/Package ID、签名证书或受控密钥证据；
3. 候选不是从干净 checkout 构建，或不能用同一命令重复得到通过结果；
4. 安装、升级、回滚、卸载、安全、隐私、许可、备份恢复或商店材料中的必需证据缺失；
5. 宣传截图不是来自该平台待审 near-final build，或与当前构建可见行为不一致；
6. Product、Engineering、Security/Privacy、Legal/License、QA/Release 五角色未签字。

工程测试通过只证明其覆盖的边界，不自动改变平台结论。`Blocked` 不得写成 `Closed`，本地 fixture 不得写成生产服务，unsigned 工程包不得写成发行候选。

## 2. 发布责任链

`config/operations.json` 是责任人和运营入口的机器事实源。姓名或公开入口为 `null` 时，表示未配备，不允许用角色名称代替真实值。

| 环节 | Accountable | Responsible | 必需动作 |
|---|---|---|---|
| 总发布决定 | Executive Owner | Release Commander | 读取五平台门禁，签署最终决定，确认撤包权限 |
| 构建与热修 | Engineering Owner | 平台工程 Owner | 干净构建、签名、哈希、SBOM、回滚包、迁移方案 |
| 安全与隐私 | Security/Privacy Owner | 安全值班 | 漏洞分级、数据影响判断、监管/用户通知建议 |
| 法务与许可 | Legal/License Owner | 法务/许可复核人 | 主体、区域、EULA、隐私、素材、第三方许可和通知时限 |
| 质量与发布 | QA/Release Owner | 平台 QA | 安装/升级/卸载/恢复矩阵、商店清单、截图一致性 |
| 支持与沟通 | Support/Comms Owner | 支持值班 | 工单分流、状态页、用户通知、FAQ、已知问题 |
| Cloud 运行 | Cloud On-call Primary | Primary/Secondary | 告警确认、缓解、流量控制、恢复和证据时间线 |

升级链固定为：值班/支持 → 平台 Owner → Release Commander → Security/Privacy 与 Legal（涉及数据、安全或法定义务时）→ Executive Owner。P0 不等待例会，P1 在 60 分钟内完成升级。

## 3. 支持时限与事故等级

| 等级 | 定义 | 确认 | 首次公开更新 | 缓解目标 | 典型触发 |
|---|---|---:|---:|---:|---|
| P0 Critical | 大规模不可用、签名/供应链被破坏、权限绕过、敏感数据泄露或不可逆数据损坏 | 15 分钟 | 30 分钟 | 4 小时 | 撤包、停更、Cloud 流量隔离，管理层与安全/法务立即加入 |
| P1 High | 核心功能严重退化、可恢复数据风险、重要隐私/许可错误、无安全绕过的广泛崩溃 | 60 分钟 | 60 分钟 | 8 小时 | 暂停批次、准备热修，至少每 2 小时更新 |
| P2 Medium | 有替代路径、影响有限、非核心功能故障 | 8 个工作小时 | 视外部影响决定 | 排入最近维护版本 | 每 2 个工作日更新工单 |
| P3 Low | 轻微缺陷、文档或体验问题 | 3 个工作日 | 通常不发状态页 | 进入产品队列 | 每 5 个工作日更新工单 |

目标不是承诺已具备团队覆盖。只要 `operations.json` 中值班、分页和公开渠道未配置，Cloud 24x7、P0/P1 响应能力即未成立。

## 4. 状态页

公共状态页必须独立于 Athena Cloud 主故障域，使用 UTC，至少包含 `operations.json` 定义的十个组件。事件消息按“调查中 → 已识别 → 监控中 → 已解决 → 复盘链接”推进，包含影响、开始时间、受影响版本/区域、临时措施和下一次更新时间；不得公布密钥、攻击细节、个人数据或未经核实的归因。

状态页模板见 `docs/ops/STATUS_PAGE_TEMPLATE.md`。在 `publicUrl` 和 provider 仍为 `null` 时，只能称为模板，不得对外声称状态页已上线。

## 5. 停更、撤包、热修、通知与复盘

### 5.1 停更

Release Commander 在以下情况立即冻结所有受影响渠道：新 P0、签名或哈希不一致、迁移破坏、商店声明与构建不一致、隐私/许可材料错误、告警不可用、证据不能复现。冻结动作包括阻止 Desktop feed 发布、停止 Steam branch promotion、停止 Cloud deploy/traffic shift、暂停 TestFlight/Play track promotion，并记录 UTC 时间、执行人和证据。

### 5.2 撤包或下架

平台 Owner 按平台能力执行撤包或停止新安装；Cloud 先保护数据和导出能力，再隔离受影响写入。已安装客户端不能假定可被远程删除；必须配套撤回公告、受影响版本识别、升级/卸载指引和支持入口。任何外部平台动作必须由真实账号授权人执行并保存平台回执。

### 5.3 热修

热修从最后批准的 tag/candidate 建立，限制为事故所需最小改动。必须重新运行适用的安全、隐私、许可、备份恢复、安装/升级、商店材料和签名验证；不得因紧急而复用旧哈希或旧截图。P0 可缩短观察批次，但不能跳过签名、P0 清零、迁移备份和双人批准。

### 5.4 通知

Support/Comms 统一状态页、应用内、官网/商店和邮件内容。安全或隐私事件先由 Security/Privacy 与 Legal 判断法定通知对象、时限和措辞。首次消息只写已知事实、用户影响、缓解动作和下一次更新时间；“无数据泄露”必须有证据后才能发布。

### 5.5 复盘

P0 在 5 个工作日、P1 在 10 个工作日内完成无责复盘。复盘包含时间线、检测缺口、根因、影响范围、恢复证据、沟通评估、可验证行动项、Owner 和截止日期。所有 P0/P1 行动项进入 `ISSUE_REGISTER.md`；未关闭 P0 自动阻止下一次相关平台发布。

## 6. 版本停止支持与服务终止

- 至少提前 180 天公告 Desktop/Steam/Mobile 的停止支持、Cloud/API 关闭或最低 OS 变化；法律或平台要求更长时取更长者。
- Desktop 1.x 权益不等于无限支持。默认支持最新稳定 1.x，以及前一个 minor 90 天；产品正式 EOL 后再提供 90 天安全修复窗口，除非高危风险要求立即停用。
- Cloud API v1 破坏性废弃至少提前 180 天，并提供迁移指南、兼容窗口和可验证导出。
- 服务终止时至少保留 90 天只读/导出窗口；不得因停服恢复已完成删除的账号数据。
- 商店下架不等于停止已安装用户支持；必须说明重新下载、许可证、导出、退款和安全更新边界。

## 7. 数据迁移政策

每次 schema 或同步协议变化必须有版本号、升级前备份、完整性校验、空间检查、幂等迁移和失败恢复测试。破坏性迁移需要 Security/Privacy、Engineering 与 QA/Release 明确批准，并在发布说明中写清不可逆点和降级策略。

Desktop 迁移失败时恢复升级前数据库，不得以空数据库继续启动。Cloud 迁移先在恢复出的 staging 副本验证，再按租户/批次推进；需保留审计链、墓碑删除语义和 deny-restore ledger。移动端在离线、token 过期、并发编辑和删除传播下都必须验证。停服或不兼容升级前必须提供机器可读导出。

## 8. 每次发布必须归档的证据

1. 精确 commit/tag、干净状态、构建环境和候选 ID；
2. 安装器/EXE/AAB/IPA/容器/Steam depot 的哈希、有效签名、时间戳和平台回执；
3. 安装、升级、卸载、回滚、安全、隐私、许可、备份恢复和故障演练完整日志；
4. 商店文案、隐私表单、AI 披露、截图与 near-final build 的映射；
5. 开放问题、例外、停止发布决定和五角色签字；
6. 若发生事故，状态页时间线、用户通知和复盘链接。

官方平台依据：Microsoft Smart App Control 要求覆盖安装、卸载和所有二进制签名测试；Steam 要求 Store Presence 与 build 分别审核且截图只能来自实际产品；Apple/Google 要求隐私披露与实际数据行为一致，支持账号创建时必须提供账号删除路径。具体链接在窗口 11 独立报告中归档。
