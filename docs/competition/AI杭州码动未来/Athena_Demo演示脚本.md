# Athena 比赛 Demo 演示脚本

## 演示目标

用一条未经伪造的真实任务链证明 Athena 能够：接收自然语言目标和多种本地资料，理解上下文，连续调用多个工具，在写入成果前暂停请求授权，把执行状态和工具证据保存在任务中，并交付一个可实际打开的 PDF 文件。

建议总时长：**3 分 20 秒**。不做功能巡游，不展示概念动画，不依赖不稳定的公网服务。

## Demo 任务推荐

### 任务名称

“把三份零散活动资料整理成一页执行简报并生成 PDF”

### 演示前准备

在专用的非敏感演示 Project 中准备并附加：

1. `活动说明.md`：活动主题、地点、目标和三条约束。
2. `人员分工.csv`：姓名、角色、联系方式；使用虚构数据。
3. `时间安排.png`：清晰的中文日程表图片，用于本地 OCR。

所有文件必须预先备份，并在录制前展示文件夹。不要使用 PDF 作为输入，因为当前项目 PDF 导入链路存在缺陷。网络开关保持关闭，模型优先使用已在现场设备验证过的本地 Ollama；若使用云模型，须在片头说明已获得模型请求与网络授权，并避免出现密钥。

### 用户输入原文

> 请读取我附加的活动说明、人员分工和时间安排图片，先提取图片中的日程，再整理成一份中文执行简报。简报必须包含：活动目标、关键约束、按时间排序的日程、人员分工、三个现场风险和检查清单。请生成 PDF，文件名为“AI杭州演示执行简报.pdf”。生成前向我请求授权；生成后报告文件路径、大小、哈希和验证状态。不要访问网络，不要修改输入文件。

这条指令故意包含目标、输入边界、结果格式、禁止事项和验收信息，便于评委判断 Agent 是否遵守约束。

## 分镜与操作步骤

| 时间 | 镜头与操作 | 屏幕应出现什么 | 解说词 |
|---|---|---|---|
| 0:00–0:15 | 桌面全屏录制，打开演示资料文件夹，再切换到 Athena 的持久化 Project。 | Windows 文件夹中三份输入；Athena 顶部显示 Project 名称而非 Temporary Chat。 | “这不是预制视频。输入是三份普通本地文件，Athena 将在一个持久化项目中完成任务。” |
| 0:15–0:35 | 将三个文件拖入聊天，停留一秒展示附件名和类型；粘贴上述目标并发送。 | 附件卡片、完整用户指令、Execute 模式与当前权限级别。 | “用户只描述目标、约束和交付格式，不逐步告诉 Agent 应该点什么。” |
| 0:35–0:55 | 不剪切地等待路由与任务建立。展开执行状态区。 | 新建 task/run、运行状态、当前步骤；不得用后期字幕替代真实 UI。 | “Athena 创建持久化任务，装载项目上下文，再让模型根据当前结果决定下一步。” |
| 0:55–1:20 | 展示 Agent 调用本地 OCR。 | `extract_text_from_images` 工具步骤、完成状态和 OCR 摘要；随后模型继续处理文本附件。 | “图片并不是交给人工抄录。Athena 调用离线 OCR，结果回到模型后再与 Markdown、CSV 内容合并。” |
| 1:20–1:50 | 展开运行步骤和工具事件，保持实时录屏。 | 至少可见一次附件/上下文处理结果、一次 OCR 结果，以及模型继续执行的状态变化。 | “每次工具返回都会改变下一步，而不是一次性播放固定脚本。任务状态、事件和证据被保存在本地。” |
| 1:50–2:15 | Athena 调用 `create_document_artifact` 时暂停。展示审批卡，人工点击批准。 | 审批请求、工具名、风险级别、PDF 文件名、目标项目目录及写入理由；每项调用有独立决定入口。 | “生成文件是持久写入，所以系统暂停并逐项展示将执行的内容；用户批准后才真正执行。” |
| 2:15–2:40 | 保持画面连续，等待生成完成。展开工具结果。 | `artifactId`、实际路径、字节数、SHA-256、`validationStatus`；PDF 成果出现在 Project artifact 区。 | “Athena 生成真实 PDF，并对文件完整性做校验，记录路径、大小和哈希。” |
| 2:40–3:00 | 在 Athena 中用 `open_path` 打开交付文件，或从成果区点击打开。 | Windows 默认 PDF 阅读器显示简报正文；标题、日程、人员、风险、清单与输入一致。 | “最后交付的不是聊天里的建议，而是 Windows 中可以打开的实际文件。” |
| 3:00–3:20 | 返回 Athena，展示 task/run 最终状态、工具事件和验证提示。 | 完成状态、持续时间、工具调用数量、成果记录；若整体任务显示 `unverified`，保留并解释。 | “当前版本能验证文件完整性，但普通任务的总体验收规则还没有完全接入。如果界面标记未验证，我们保留这个提示，不把模型停止执行等同于全部验收通过。” |

## 必须保留的真实证据

以下画面不要剪掉，否则评委很难区分真实执行与预录结果：

1. 用户点击发送后，到首次工具状态出现之间的连续画面。
2. OCR 工具从运行到完成，以及 OCR 结果进入后续处理的连续变化。
3. 生成 PDF 前的等待审批状态、人工批准动作和批准后的恢复。
4. PDF 生成中的短暂等待与最终真实文件路径。
5. 从 Athena 打开 Windows 默认 PDF 阅读器的过程。
6. 任务最终状态、文件大小、哈希、验证状态和工具事件列表。
7. 录制前与录制后同一输出目录的对比；可让资源管理器显示“修改日期”和文件大小。

允许加速的只有模型等待时间较长的静默片段。若加速，应在画面上明确标注“2× 实时录屏加速”，不能跳过工具调用、审批或文件生成节点。

## 现场设置建议

- 分辨率建议 1920×1080，Windows 显示缩放 100% 或 125%，字体至少保证评委能看清工具名与路径。
- 提前清理通知、真实用户名、密钥、历史聊天和私人路径；演示账户只放虚构资料。
- 使用固定、短的本地 Project 名称，例如“比赛演示｜活动简报”。
- 关闭外部网络，使用已下载并现场预热过的本地模型与 OCR 数据，减少不可控因素。
- 保留鼠标指针与系统时钟，避免大量跳切。
- 预备一次完整无剪辑备份录屏；主视频可轻微压缩静默时间，但证据链不删。

## 当前版本的演示风险与处理

### 风险一：审批能力缺少现场素材

当前源码已实现逐项审批卡，可展示命令、工作目录、路径、URL、请求方法和受限长度的写入预览，并支持逐项批准/拒绝；敏感信息会遮蔽。类型检查、Agent/工具测试、桌面 smoke 与固定模型夹具驱动的真实 Renderer E2E 已通过，但现有仓库素材还没有这张最终构建截图。比赛前必须补拍，并核对卡片显示参数与实际执行事件一致。

### 风险二：计划展示不够细

当前用户任务只创建一个通用起始步骤，细化过程由模型在工具调用中动态形成。视频可展示真实工具事件与状态流，但不要把它解说成“系统已先生成完整可编辑计划”。

### 风险三：总体任务可能显示未验证

文档工具会验证生成文件的完整性并记录 SHA-256，但普通任务的总体 `validation` 默认可能为空。若最终显示 `unverified`，应保留这一画面，并解释为“文件完整性已验证，内容是否完全满足用户定义的验收标准仍需复核”。

### 风险四：真实设备与模型波动

在比赛同一台机器上至少完整跑通三次；记录模型名称、平均耗时、最长耗时和失败原因。不要在正式 Demo 中临时切换未验证的云供应商。

## 不建议作为主 Demo 的内容

- 不用“打开记事本并自动点击菜单”作为卖点：当前没有通用 GUI 鼠标键盘控制。
- 不把空状态 UI、概念图或品牌图当作能力证明。
- 不依赖 PDF 输入解析、公开网页抓取、Live2D 或 Athena Cloud 生产服务。
- 不用几十个一秒钟的小功能剪辑代替一条完整任务链。
- 不展示删除真实文件、修改启动项或 Shell profile 等不必要的高风险操作。

## 备用 Demo

若现场文档生成链受环境影响，可改用“本地服务诊断报告”：让 Athena 读取一个演示项目的配置，执行 `check_port`、`http_request` 和安全的只读诊断命令，整理证据并生成 Markdown 报告。该备用方案仍可展示连续工具调用、真实 Windows 环境反馈和最终文件交付，但多模态与 OCR 表现会较弱。
