# Athena「AI+超级智能体」赛道能力映射

参赛院校：西安翻译学院

专业：数字媒体艺术

团队成员：鲁滨、唐婧、贾晨泽、汪昊

指导教师：席晶（授课老师）

项目版本：`0.9.7-beta.1`  
评估基线：2026 年 9 月 18 日当前仓库、源码检查与本地验证结果

评估原则：实现存在不等于现场可用；夹具测试不等于真实供应商；规划项不计入当前能力。

## 1. 任务理解

- **Athena 当前能力：** 能在 Project 上下文中接收自然语言目标、附件和项目记忆，并把 Execute 请求送入持久化 Agent 链。入口路由优先使用规则；可选的语义路由默认关闭，且仅复核中置信度普通对话。
- **代码/模块依据：** `src/core/routing/AgentMessageRouter.ts`、`src/core/controller/AthenaController.ts`、`src/core/ai/ContextManager.ts`。当前路由测试覆盖 45 个夹具，结果为 accuracy 1.000、safety false positives 0。
- **当前优势：** 任务理解不脱离项目、权限和附件边界；Execute 路径要求持久化 Project 与明确同意。
- **当前缺陷：** 规则路由对开放域表达的泛化能力没有真实用户集证明；夹具准确率不能代表开放域准确率。
- **比赛前最值得补的内容：** 建立 50—100 条来自真实用户的中文复杂目标集，报告路由、信息抽取、约束遵守和澄清触发率，并保存失败样本。

## 2. 自主规划

- **Athena 当前能力：** `AgentRunner` 通过模型原生工具调用循环动态决定下一步，接收工具结果后继续调整；默认预算为 16 轮模型调用和 48 次工具调用，耗尽后暂停，由用户选择追加同等预算或停止并总结。
- **代码/模块依据：** `src/core/agent/AgentRunner.ts`、`src/core/agent/ProjectWorkspaceService.ts`。
- **当前优势：** 规划与真实执行结果相连，支持审批暂停、失败收敛和恢复，而非一次性静态 JSON 计划。
- **当前缺陷：** 创建用户任务时只有“Execute the agreed goal”通用起始步骤，缺少执行前可审阅、可编辑的细粒度计划；工具事件不等于完整计划模型。
- **比赛前最值得补的内容：** 增加结构化计划实体与 UI，显示步骤、依赖、风险、预计工具和验收条件，并把运行事件回填到计划。

## 3. 工具调用

- **Athena 当前能力：** 具有注册化 ToolRegistry，模型通过原生 `tool_calls` 调用计算机、文档、OCR、Skill、MCP 和研究工具；参数按 schema 校验，工具带版本、能力、风险与审批策略。
- **代码/模块依据：** `src/core/agent/ToolRegistry.ts`、`src/core/agent/AgentRunner.ts`、各 `*AgentToolBridge.ts`。
- **当前优势：** 工具不是提示词中的虚拟动作，而是可执行、可记录、可审批的运行单元；自动重试限制在安全或幂等工具。
- **当前缺陷：** 当前源码已把命令、路径、URL、写入预览等关键参数接入逐项审批 UI，并支持逐项批准/拒绝；真实 Renderer 的固定夹具 E2E 已通过，但现有素材尚无最终构建截图，Skill 也只加载文本说明和资源，不自动执行技能脚本。
- **比赛前最值得补的内容：** 当前源码构建已完成命令与文件修改审批录屏；下一步是在最终候选安装包复现“schema 参数—风险解释—审批卡—实际事件”，并增加多任务真实模型工具选择基准。

## 4. 环境交互

- **Athena 当前能力：** 22 个 Windows 工具覆盖文件信息、目录、读写、搜索、复制、移动、删除、命令、持久终端、程序启动、路径打开、HTTP 与端口检查。
- **代码/模块依据：** `src/core/tools/ComputerToolCatalog.ts`、`src/core/tools/ComputerTools.ts`、`src/core/tools/AgentComputerTools.ts`。
- **当前优势：** 已能对真实文件系统、Shell 和网络端点采取动作，足以完成大量可命令化个人工作流。
- **当前缺陷：** 没有通用鼠标、键盘、屏幕截图理解或任意 GUI 控制；“操作 Windows”不能表述为“能操控所有 Windows 应用”。
- **比赛前最值得补的内容：** 短期先打磨文件/终端闭环并做好证据；GUI 自动化只有在屏幕隐私、坐标漂移、确认机制和失败恢复具备后再纳入赛道主张。

## 5. 结果交付

- **Athena 当前能力：** 可保存任务结果、证据与交付物；文档工具可生成 Markdown、HTML、DOCX、PDF，并记录路径、字节数、SHA-256 和完整性验证。
- **代码/模块依据：** `src/core/artifacts/ArtifactAgentToolBridge.ts`、`DocumentArtifactService.ts`、`ArtifactWorkspaceService.ts`、`AgentStore.ts`。
- **当前优势：** 能交付真实文件，不止是聊天文本；成果与 task/run/step 关联，可追溯。
- **当前缺陷：** PDF 输入导入当前损坏；部分任务没有内容级验收，只能证明文件完整，而不能证明业务要求全部满足。
- **比赛前最值得补的内容：** 修复 PDF 导入和假绿测试；为 Demo 模板增加内容级检查，例如必备章节、数据行数、文件存在与哈希。

## 6. 任务闭环

- **Athena 当前能力：** 从用户目标、Project 上下文、模型调用、工具执行、审批、事件持久化到成果记录已形成主链；支持取消、失败、受控恢复和权限撤销。
- **代码/模块依据：** `src/core/controller/AthenaController.ts`、`src/core/agent/AgentRunner.ts`、`src/core/agent/AgentStore.ts`。
- **当前优势：** 任务状态是持久化对象，审批不是弹窗旁路，恢复也有不确定重放保护。
- **当前缺陷：** 当普通任务未配置 required validations 时，即使工具步骤都完成，总体也只能得到 `unverified`；若存在未恢复的失败或拒绝步骤则标记 `issues`。这使“执行闭环”成立，但“自动验收闭环”不完整。
- **比赛前最值得补的内容：** 让用户目标生成可见验收条件，并在结束前调用对应检查工具；将 verified/issues/unverified 的证据直接展示给用户。

## 7. 创新性

- **Athena 当前能力：** 以本地优先架构把多模型、受控工具、持久化任务、多层记忆和成果交付放在同一 Windows 产品中。
- **代码/模块依据：** Electron 主/渲染进程架构、Agent 与 ToolPolicy、SQLite schema v20、模型适配器、记忆模块。
- **当前优势：** 创新集中在“可管理的个人 Agent 工作环境”，而不是单点模型能力；特别是权限上限收紧、审批恢复和结果可信度标记具有产品化意义。
- **当前缺陷：** 缺少真实用户对比数据，无法量化相对 Chatbot 节省的时间或步骤；GUI 能力弱于部分屏幕自动化产品。
- **比赛前最值得补的内容：** 用 3 个复杂任务做同人同机 A/B：纯 Chatbot 指导 vs Athena 执行，记录人工操作次数、完成时间、错误数和结果可追溯性。

## 8. 实际应用价值

- **Athena 当前能力：** 适合资料整理、文件归档、开发环境诊断、项目续作、文档交付等可文件化或可命令化任务。
- **代码/模块依据：** Computer Tools、Artifact Tools、Project Workspace、Memory、OCR 与附件实现。
- **当前优势：** 贴近日常个人工作流，能够在一个任务里组合多个动作；本地优先适合敏感资料和离线场景。
- **当前缺陷：** 尚无受控 Beta 用户的完成率、留存、节时或满意度数据；应用价值目前主要由功能链与测试推断。
- **比赛前最值得补的内容：** 招募 10—20 名校内体验者，使用固定任务包，统计成功率、人工接管次数、平均用时和最常见失败点。

## 9. 技术完成度

- **Athena 当前能力：** 当前源码可通过类型检查、Agent/工具/工作区/路由/模型适配/记忆/附件/OCR/成果/语音等测试，Electron smoke 通过并出现 `ATHENA_SMOKE_READY_TO_SHOW`、`ATHENA_SMOKE_DOM_OK`。
- **代码/模块依据：** `package.json` 测试脚本、`scripts/verify-*.js`、Electron smoke；项目版本 `0.9.7-beta.1`，数据库 schema v20。
- **当前优势：** 已跨越纯原型阶段，核心模块有实现、接线和回归测试，主进程可以实际启动。
- **当前缺陷：** `test:project-documents` 通过脚本附加固定成功标记，直接验证脚本会静默退出，无法证明断言完成；PDF 导入确有缺陷。供应链检查、签名发行、干净机器和真实云供应商证明不足。
- **比赛前最值得补的内容：** 修复 PDF 链路和所有假绿测试；现有 DeepSeek 虚构代码任务 live E2E 已通过并录屏，但仍需在最终安装包和比赛同机重复三次，并补文档/OCR/PDF 类型任务。

## 10. 安全性

- **Athena 当前能力：** 权限等级默认 off；仅 Execute 可获得计算机权限；模型请求、外部网络、高风险工具分别受同意或审批控制；凭据用 `safeStorage` 加密；Renderer 使用 sandbox/context isolation 且不直接获得密钥。
- **代码/模块依据：** `src/core/config/SettingsStore.ts`、`src/core/agent/AgentPolicyEngine.ts`、`src/core/agent/AgentRunner.ts`、`src/core/controller/AthenaController.ts`、`src/core/tools/AutoExecutedLocations.ts`、`src/shared/agentRunPresentation.ts`、`src/renderer/app.ts`、`src/app/main.ts`。
- **当前优势：** 权限与任务运行绑定，运行中撤权可收紧权限上限；不确定重放采用关键等级审批。
- **当前缺陷：** 当前源码已实现逐项参数展示、敏感信息遮蔽、追加写入审批和自动执行位置识别，并通过逐项审批 Renderer E2E；现有录屏来自当前源码构建，不是最终签名安装包，且尚未逐一覆盖全部自动执行位置。这不是经过第三方认证的安全沙箱。
- **比赛前最值得补的内容：** 扩展 UI 级测试与录屏，覆盖 Startup、PowerShell/Shell profile、Git hooks、快捷方式等自动执行位置，并核对显示参数与实际事件。

## 综合 readiness 评估

### 等级：**B**

**含义：具备真实参赛原型和有说服力的 Agent 主链，但尚未达到 A 级“现场稳定、闭环可验收、安全交互完整”的状态。**

给出 B 而不是 C，是因为 Athena 已有真实 Electron 应用、原生工具循环、持久化任务、22 个 Windows 工具、逐项审批、多层本地记忆和文档成果，且当前源码类型检查、Agent/工具测试、隔离夹具 Renderer E2E 与一条 DeepSeek live E2E 通过，真实审批截图和视频已经生成。没有给 A，是因为计划和产品内验收闭环不完整，PDF 输入链路与测试可靠性有明确缺陷，而且缺少最终签名构建录屏、真实用户、真实音频设备、比赛设备重复测试和签名发行证据。S 级目前不成立。

### 面向评委的客观判断

| 维度 | 评估 | 判断依据 |
|---|---|---|
| Agent 核心链 | A- | 连续工具调用、状态、审批、恢复真实存在 |
| Windows 执行 | B+ | 文件与命令能力完整；无通用 GUI |
| 计划与验收 | C+ | 动态规划存在；可视计划与自动验收不足 |
| 本地记忆 | B | 分层与隔离扎实；默认语义召回弱 |

| 安全与权限 | B+ | 架构边界和逐项审批已有 Renderer E2E；自动执行位置与最终构建证据仍不足 |

## 比赛前优先级最高的 5 个改进项

1. **P0｜补齐计划与验收闭环。** 创建可审阅的结构化计划，为 Demo 任务生成明确验收条件；结束前自动核对文件存在、大小、哈希、章节和关键数据，并显示证据。
2. **P0｜修复 PDF 输入链路与假绿测试。** 修正 pdfjs 资源销毁调用，让直接验证脚本在所有断言完成后输出唯一成功标记；禁止 package script 伪造成功输出。
3. **P0｜把现有源码 Demo 升级为比赛级证据。** 当前 DeepSeek 代码修复任务已通过一次 live E2E；仍需在最终候选安装包和同一比赛设备连续跑通三次，并补真实本地模型、附件、OCR 和 PDF 交付任务，记录失败与人工接管。
4. **P1｜扩展新安全交互证据。** 在现有逐项审批 Renderer E2E 上增加参数遮蔽、批量批准、追加写入和所有自动执行位置场景，并补拍最终构建画面。
5. **P1｜增强语义记忆并补用户数据。** 用真实本地向量模型改善同义改写召回，并以 10—20 名体验者的完成率、人工接管次数和耗时验证应用价值。

## 结论

Athena 当前最有竞争力的部分，是已经存在的“模型原生工具调用 + Windows 文件/命令执行 + 持久化任务状态 + 用户审批 + 本地记忆 + 文件成果”组合。比赛材料应围绕一条真实、连续、可复核的任务链，而不是扩大到“能操控任意软件”或“已经完全自主验收”。如果完成上述三项 P0 工作，Readiness 有机会从 B 提升到 A-；在此之前，最好的参赛策略是用真实闭环证明能力，同时主动披露边界。
